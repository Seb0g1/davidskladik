# План: идеальный фид Avito с корректными категориями

Цель: товары, импортируемые Ozon → Avito, попадают в фид Автозагрузки с полностью
корректной категоризацией (все обязательные теги категории заполнены валидными
значениями), фид проходит загрузку без ошибок, а остатки/цены/заказы/чаты/отзывы
работают через API.

Источник требований: сохранённые страницы шаблонов Автозагрузки в `avito/*.html`
(по одной на конечную категорию) + доки API (`avito/авторизация.html`,
`остатки.html`, `управление заказами.html`, `мессенджер avito.html`, `отзывы.html`,
`avito1-doc.txt`, `avito2-doc.txt`).

## Важные факты, выясненные при разборе HTML

1. **Имена файлов сдвинуты относительно содержимого** (сохранялись со сдвигом на
   один клик): например, `духи и туалетная вода.html` внутри описывает
   «Атомайзеры и флаконы», `маски.html` → «Патчи», `дезодорант.html` →
   «Уход за телом / Дезодоранты». Справочник строим **только парсингом содержимого**
   (блок «Одно из значений» в `id="field-XXX"`), имена файлов игнорируем.
2. Категоризация Avito в фиде — цепочка тегов, а не одно поле:
   - `Category` = «Красота и здоровье» (всегда);
   - `GoodsType` = «Парфюмерия» → далее `PerfumeryType` (+ обязательный `Condition`);
   - `GoodsType` = «Уход и гигиена» → далее `GoodsSubType`, а для «Уход за лицом» /
     «Уход за телом» ещё и `SubType`;
   - `GoodsType` = «Средства для волос» — без подтипов (проверить по API).
3. Текущий `buildAvitoAdXml` (`server/parts/02a-avito-feed-build.js`) пишет только
   `Category` + `GoodsType` из feedDefaults — все товары падают в одну категорию.
4. Страницы, вероятно, сохранены с фильтром «Только обязательные» — полный список
   опциональных полей категории надо добирать через API Автозагрузки
   («Получение полей категории», «Получение дерева категорий» — методы есть в доке).
5. `уход за телом.html` сохранился без блоков полей (битый); страниц «Бритьё и
   эпиляция», «Лосьоны, спреи и молочко», «Средства для душа и ванны» нет (только
   `_files`), но их значения присутствуют в других страницах из-за сдвига.

## Этап 0. Справочник категорий (source of truth)

- Скрипт `scripts/avito-parse-category-specs.cjs`: парсит `avito/*.html`
  (блоки `id="field-<Tag>"`: обязательность, «Одно из значений», описание) и
  собирает `server/data/avito-category-specs.json`:
  ```json
  {
    "categories": [
      {
        "key": "parfum-edt",
        "label": "Парфюмерия / Духи и туалетная вода",
        "tags": { "Category": "Красота и здоровье", "GoodsType": "Парфюмерия", "PerfumeryType": "Духи и туалетная вода" },
        "required": ["Condition", "AdType", "Brand", "..."],
        "optional": ["Volume", "Gender", "..."]
      }
    ]
  }
  ```
- Валидация справочника против живого API Автозагрузки (клиент
  `02a-avito-autoload-api.js` уже есть): «Получение дерева категорий» +
  «Получение полей категории» — добираем полные списки допустимых значений и
  опциональные поля, фиксируем расхождения с HTML.

## Этап 1. Классификатор товара → категория Avito

Новый модуль `server/parts/02a-avito-categorizer.js`:

- Вход: товар склада (name, brand, `raw` с категорией Ozon
  `description_category_id`/`type_id`).
- Сигналы, по приоритету:
  1. маппинг категории Ozon → категория Avito (таблица в
     `avito-import-rules.json`, редактируется в UI);
  2. правила по ключевым словам названия (упорядоченный список, первое совпадение):
     «духи|парфюмерная вода|туалетная вода|edp|edt|parfum|одеколон» → Духи и
     туалетная вода; «атомайзер|флакон» → Атомайзеры и флаконы; «диффузор|саше» →
     Диффузоры, спреи и саше; «парфюмерное масло|attar|масляные духи» →
     Парфюмерные масла; «набор» (+парфюм-контекст) → Парфюмерные наборы;
     «крем для лица» → Уход за лицом/Кремы; «крем для рук|для тела» → Уход за
     телом/Кремы; «сыворотка|эссенция» → Сыворотки и эссенции; «тоник|мицелляр» →
     Тоники и лосьоны; «маска для лица» → Маски; «патчи» → Патчи;
     «скраб|пилинг|гоммаж» → Скрабы и пилинги (лицо/тело по контексту);
     «умывани|очищающ» → Средства для умывания; «шампунь|кондиционер|бальзам для
     волос|маска для волос» → Средства для волос; «дезодорант|антиперспирант» →
     Дезодоранты; «мыло» → Мыло; «гель для душа|пена для ванн» → Средства для душа
     и ванны; «зубн|ополаскиватель для полости» → Уход за полостью рта;
     «spf|солнцезащит|загар|автозагар» → Загар и защита от солнца; «патчи|маска»
     и пр.;
  3. дефолт из правил (для парфюм-ассортимента — «Духи и туалетная вода»):
     товар без уверенной классификации кладём в дефолтную категорию (решение
     оператора), но помечаем флагом `categoryAutoDefaulted` — в UI отдельный
     фильтр, чтобы такие товары можно было быстро просмотреть и поправить.
- Особое внимание «Парфюмерным наборам»: слово «набор»/«set»/«kit» в
  парфюм-контексте (духи, edp/edt, миниатюры) → «Парфюмерия / Парфюмерные
  наборы»; «набор» в уход-контексте (кремы, маски, уход) → «Уход и гигиена /
  Наборы уходовой косметики». Правило набора приоритетнее одиночных категорий,
  чтобы наборы не улетали в «Духи и туалетная вода».
- Выход: `categoryKey` из справочника этапа 0 + автозаполненные атрибуты:
  `Condition` = «Новое», `AdType` = «Товар от производителя» (решение оператора),
  `Volume` из `parseVolumeMlFromText`, `Gender` по названию (муж/жен/унисекс),
  `Brand` из товара.
- Результат сохраняется в листинге (поля `categoryKey`, `goodsSubType`,
  `subType`, `perfumeryType`, `categoryAutoDefaulted`), с возможностью ручного
  override (`categoryLocked`), — при повторном импорте ручной выбор не затирается.

## Этап 1.5. Миграция листингов в Postgres

Объявлений будет очень много (решение оператора) — JSON-файл не подходит:

- Новая модель Prisma `AvitoListing` (adId PK, sourceProductId FK →
  WarehouseProduct, title, description, brand, volumeMl, priceRub, imageUrls Json,
  categoryKey, goodsType/goodsSubType/subType/perfumeryType, condition, adType,
  extraFields Json, enabled, outOfStock, categoryLocked, categoryAutoDefaulted,
  lastSyncedAt, createdAt/updatedAt) + индексы по sourceProductId, categoryKey,
  enabled. Отдельная модель чище, чем расширение enum `Marketplace`, — у листинга
  своя семантика и связь с товаром-источником.
- Миграция `avito-listings.json` → Postgres одноразовым скриптом
  (`scripts/migrate-avito-listings.cjs`), feedToken переезжает в настройки.
- `02a-avito-listings-storage.js` переводится на Prisma; сборка фида читает
  листинги стримом/батчами, кэширует готовый XML (инвалидация по updatedAt),
  чтобы Авито не ждал генерацию на десятках тысяч объявлений.

## Этап 2. Генерация фида по спецификации категории

- `buildAvitoAdXml`: теги категоризации берём из спецификации `categoryKey` —
  выводим ровно те теги, которые входят в спецификацию (никаких `GoodsSubType`
  у парфюмерии и `PerfumeryType` у ухода).
- Preflight-валидатор фида: для каждого объявления проверка обязательных полей и
  допустимых значений по справочнику; эндпоинт `GET /api/avito/feed/validate` с
  отчётом (ok / warnings / errors по объявлениям). Невалидные объявления в XML не
  попадают (настройка), чтобы одна ошибка не портила загрузку.
- Решить и зафиксировать `AdType`: «Товар от производителя» vs «Товар приобретён
  на продажу» (для перепродажи корректнее второе — уточнить допустимые значения
  через API и согласовать с оператором).
- Опционально: поля Авито Доставки (Weight/Length/Height/WidthForDelivery) из
  дефолтов правил.

## Этап 3. Замкнутый цикл через API Автозагрузки

- В `02a-avito-autoload-api.js` дописать: «Загрузка файла по ссылке» (форс-запуск),
  «История загрузок» v4, «Объявления загрузки» с ошибками.
- Ошибки категоризации/валидации из отчётов Авито показываем в UI рядом с
  листингом — критерий готовности: 0 ошибок в отчёте загрузки.

## Этап 4. Остатки и цены через API (`остатки.html`)

- Пуш остатков/цен по API «Управление остатками» после изменений на складе
  (дополнительно к фиду, чтобы не ждать скачивания XML по расписанию).
- Переиспользовать механику фонового рефреша `02f-avito-feed-refresh.js`.

## Этап 5. Заказы, мессенджер, отзывы (`управление заказами.html`, `мессенджер avito.html`, `отзывы.html`)

- Заказы: получение списка/статусов, отображение в существующем разделе заказов.
- Мессенджер: webhook-подписка, чтение и ответы — встроить в существующую
  страницу чатов.
- Отзывы: получение и ответы — в существующий раздел отзывов/вопросов.

## Этап 6. Frontend (страница Avito)

- Таблица листингов с колонкой категории (полный путь), фильтр
  «не классифицировано», ручной выбор категории (каскадный селект по справочнику),
  массовое назначение.
- Редактор правил: маппинг Ozon-категория → Avito, ключевые слова, дефолт.
- Экран preflight-отчёта + отчёты загрузок Авито.

## Порядок работ

1. Этап 0 (парсер + справочник + сверка с API) — фундамент, без него остальное
   не имеет смысла.
2. Этап 1 + 2 (классификатор, хранение, фид, preflight) — основной результат:
   «категории ставятся идеально».
3. Этап 3 (отчёты загрузок) — контроль качества.
4. Этап 6 (UI) — параллельно с 1–3 по мере готовности API.
5. Этапы 4–5 — после стабилизации фида.

## Открытые вопросы (согласовать до реализации)

1. `AdType`: «Товар от производителя» или «Товар приобретён на продажу»?
2. Нужен ли `Condition` = «Б/у» где-либо (по умолчанию везде «Новое»)?
3. Листинги остаются в `avito-listings.json` или мигрируем в Postgres
   (добавить `avito` в enum `Marketplace`)? Для сотен объявлений JSON ок,
   для тысяч — лучше Postgres.
4. Товары без уверенной классификации: не выгружать (рекомендуется) или
   выгружать в дефолтную категорию?
