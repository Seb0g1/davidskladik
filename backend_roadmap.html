P0
PM-снапшот удаляется до вставки — нет транзакции, возможна пустая таблица
02a-snapshot-core.js:170 data-loss
priceMasterSnapshotItem.deleteMany({}) удаляет все ~30к строк, затем createMany вставляет порциями по 2000. Если вставка падает (сеть, OOM, сигнал завершения), таблица остаётся пустой. Все последующие прайсы и поиск по снапшоту вернут 0 результатов — пока снапшот не обновится снова.

Ожидаемое поведение: операция должна выполняться в одной транзакции (или через UPSERT / staged swap) чтобы атомарно заменить данные без окна «пустой таблицы».
P0
POST /api/warehouse/products возвращает весь склад в ответе
02d-warehouse-products-crud.js:47 data-leak · performance
response.json({ ok: true, product: freshProduct, warehouse }) — поле warehouse содержит весь каталог (все товары + поставщики). При каталоге ~14k товаров ответ весит сотни МБ JSON и передаётся клиенту на каждое сохранение карточки. Риски:
— Memory pressure: сериализация всего каталога на каждый запрос.
— Data leak: все внутренние поля (цены, поставщики, история) видны любому аутентифицированному пользователю.
— Frontend OOM: браузер получает огромный JSON и может зависнуть.

Фронтенд, скорее всего, использует только поле product — поле warehouse надо убрать из ответа.

Партнёрский итог комиссионки считается по операциям ВСЕХ партнёров
02d-consignment-routes.js:1532 logic · wrong-data
Эндпоинт GET /api/consignment/partner-summary?partnerId=X (Bot API) фильтрует consignmentItem по partnerId, но загружает все 50 000 операций без фильтра:

Затем consignmentSummaryFromRows(items, ops) суммирует ops (все операции всех партнёров), а не только операции по товарам данного партнёра. Результат: неверные баланс, выручка, прибыль для партнёра — он видит агрегат по всей комиссионке.
P1
PM Price Monitor обнаруживает изменение цены, но не запускает перерасчёт
02f-pm-monitoring-scheduler.js:36 logic · stale-price
runPmPriceChangeMonitor сравнивает сохранённую цену поставщика с живой MySQL, логирует pm_price_changed, но не ставит задачу перерасчёта (не вызывает queueAuthoritativePriceReprice или аналог).

Комментарий в файле говорит «reprice cycle should be triggered by the normal price sweep» — но sweep пропускает SKU с актуальным priceVerifiedAt на 6 ч (PRICE_SWEEP_VERIFIED_COOLDOWN_HOURS). Если цена поставщика выросла после последней верификации, новая цена попадёт на маркетплейс только через ~6 часов, а не ~2 минуты, как подразумевает дизайн.
P1
LIMIT в notifications-core через шаблонную строку вместо параметра
02f-notifications-core.js:65 sql-injection-pattern
LIMIT ${limit} в $queryRawUnsafe, где limit вычислен через Math.max(1, Math.min(100, Number(request.query.limit))). Значение числовое и граничит, реальной инъекции нет — но паттерн опасен: если позже кто-то ослабит валидацию или добавит другой параметр аналогично, инъекция станет возможной. Надо заменить на $N с передачей в параметры.
P1
ids.join(",") в UPDATE app_notifications — числа без параметризации
02f-notifications-core.js:91 sql-injection-pattern
WHERE read_at IS NULL AND id IN (${ids.join(",")}) — массив ids фильтруется через Number.isFinite && id > 0, поэтому реальной инъекции нет. Но паттерн нарушает принцип parameterized-only и может стать опасным при рефакторинге. Prisma поддерживает $queryRaw\`\` с автоматическим escape для массивов через Prisma.join(ids).
P1
Числовые параметры через шаблонные строки в $queryRawUnsafe (системные)
02f-error-audit.js:89,94,124,152 · 02f-price-sweep.js:39,44 · 02f-stock-sweep.js:47 sql-injection-pattern
Семь файлов используют числовые переменные окружения/env в шаблонных строках SQL: interval '${windowDays} days', LIMIT ${batchLimit * 3}, interval '${priceSweepVerifiedCooldownHours} hours' и т.д. Все значения прошли Math.max/Math.min/Number() и не содержат инъекций. Но паттерн системно неверный — при добавлении нового параметра без валидации появится реальная уязвимость. Все числа должны передаваться через $N-параметры.

WB-синк: не атомарен — stocks и prices обновляются раздельно
02f-wb-sync.js:79 race-condition · atomicity
runWbMarketplaceSync обновляет остатки (wbUpdateStocks), а затем цены (wbSetPrices) отдельными запросами. Если процесс завершается или WB возвращает ошибку между этими двумя вызовами: остатки выставлены (5 шт.), а цены не обновлены (могут быть стальными или 0). Покупатели видят товар с неверной ценой.
P2
priceSweepVerifiedCooldownHours=0 разрешён и заполняет очередь бесконечно
02f-price-sweep.js:23 logic · queue-flood
Math.max(0, Number(process.env.PRICE_SWEEP_VERIFIED_COOLDOWN_HOURS || 6) || 6) — минимум 0. При PRICE_SWEEP_VERIFIED_COOLDOWN_HOURS=0 в SQL генерируется interval '0 hours' — все недавно верифицированные товары сразу же переходят в кандидаты повторно. Каждый тик sweep (раз в 2 мин) ставит в очередь до 500 SKU повторно, даже если цена не менялась. Очередь BullMQ переполняется.
P2
Price-send finish: readWarehouse() может не содержать только что добавленный товар
02d-prices-send-warehouse-finish.js:3 race-condition · stale-cache
После отправки цен вызывается readWarehouse() для поиска продуктов по id (warehouse.products.find(entry => entry.id === item.id)). В api-процессе (postgresOnly) склад — это частичный in-memory кэш. Если продукт был создан недавно и ещё не попал в кэш, поиск вернёт undefined — цена-история не запишется, статус отправки не обновится. Баг молчит: нет ни ошибки, ни предупреждения.

Мёртвое добавление client-ключа в deleteKeys при удалении ссылки
02d-warehouse-links-mutation.js:122 logic · dead-code
После того как правильный серверный ключ добавлен (deleteKeys.add(warehouseLinkTargetKey(link))), следующей строкой добавляется ref.linkTargetKey (ключ из фронтенда, другой формат):

Комментарий на строках 115–121 объясняет, что форматы различаются и ключ фронтенда никогда не совпадёт с серверным. Добавление мёртвое — работает только потому что серверный ключ уже добавлен. Потенциально вводит неверный ключ, который может случайно совпасть с другой ссылкой при рефакторинге.

P3
consignmentSummaryFromRows: возврат товара дважды влияет на profitTotal
02d-consignment-routes.js:69 logic · wrong-data
При типе операции "return":
acc.salesRevenue -= op.unitSale * op.quantity (правильно — снижает выручку)
acc.profitTotal += op.sponsorDelta + op.myDelta — но у возврата sponsorDelta и myDelta отрицательные (реверс прибыли). Таким образом profitTotal складывает отрицательное число, снижая прибыль. Одновременно balance += op.balanceDelta (в общем цикле) тоже учитывает возврат. В зависимости от того, как формируются balanceDelta и sponsorDelta у возврата, возможно двойное вычитание из итоговой прибыли. Требует проверки бизнес-логики.
