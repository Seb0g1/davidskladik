# ProblemProductsPage — Plan

## Current State

Страница «Проблемные товары» — единая диагностическая таблица SKU по всем маркетплейсам. Получает список товаров с проблемами из `/api/problem-products` (источник: Postgres `salesAutomationSkuState` или preview-dry-run через `sendWarehousePrices`), позволяет фильтровать по категории проблемы через `<SelectField>`, выбирать чекбоксами нужные товары и отправлять их в repair-job через `/api/problem-products/repair`.

## Bugs / Issues Found

- **`visibleItems` — мёртвая переменная** — строка 62: `const visibleItems = items;` — полная копия массива без фильтрации, хотя поле поиска `q` передаётся в запрос на бэкенд. Если бэкенд не вернул отфильтрованных результатов (например, `previewFallback`-ветка не поддерживает `q`), клиент не предоставляет никакого локального поиска. Переменная существует, но ни к чему не применяется иначе. Кнопка «Выбрать все» использует `visibleItems` (строка 115), но это всегда все загруженные товары.

- **Чекбокс «Выбрать все» проверяет неверное условие** — строка 115: `visibleItems.every(i => !text(i.productId || i.id) || selected.has(...))`. Условие «every» включает товары, у которых `productId` пустой (`!text(...)` даёт `true`). Это значит: если хотя бы один товар не имеет `productId`, чекбокс может показать себя «checked», даже когда реально ничего не выбрано.

- **`add`/`remove` объявлены, но нигде не используются кроме `onChange` чекбокса «все»** — строки 60–61: функции `add` и `remove` есть, при этом в самом `onChange` строки 116 они всё равно inline-вызываются через тернарный оператор, а не через именованные функции. Это дублирование логики между `toggle`, `add`, `remove`.

- **Предупреждение «первые 100» показывается даже для repair без бэкенд-ограничения по типу** — строка 99: сообщение `«Будут починены первые 100 из {selected.size} выбранных»` корректно, но бэкенд (строка 316 сервера) `productIds.slice(0, 100)` отрезает молча без ошибки. Само предупреждение появляется только когда `selected.size > 100`, что правильно — но пользователь не получает никакого уведомления о результатах отброшенных товаров после завершения job.

- **`repair.data` отображает результат даже после следующего рефетча** — строки 104–110: `repair.data` не очищается при смене фильтра `category` или после `invalidateQueries`. Успех-стрип остаётся на экране бесконечно, пока пользователь не запустит новый repair.

- **Нет строки поиска на клиенте** — бэкенд принимает параметр `q`, но клиент его не передаёт в запрос (строка 35: в params только `category` и `limit`). Поле `q` в `URLSearchParams` не добавляется, хотя на бэкенде фильтрация по нему реализована.

- **`label()` не покрывает `in_retry`** — строка 254 бэкенда: `category === "price_retry" ? "in_retry" : category` — бэкенд хранит `reason = "in_retry"`, но `label()` на фронтенде (строки 14–25) содержит только `"price_retry"`. Если бэкенд вернёт `reason: "in_retry"`, лейбл в колонке «Причина» покажет сырую строку `in_retry` вместо русского текста.

## Improvement Ideas

- **[HIGH]** Добавить поле поиска на клиенте — `<input>` для `q`, передавать в `URLSearchParams` и debounce-задержкой 300 мс. Сейчас параметр есть на бэкенде, но недоступен из UI.

- **[HIGH]** Добавить `repair.reset()` при смене `category` или при успехе через `onSuccess` — чтобы стрип с результатом не накапливался.

- **[MEDIUM]** Исправить `label()` — добавить `in_retry: "retry цен"` чтобы синхронизировать с бэкенд-значением.

- **[MEDIUM]** Унифицировать чекбокс-логику: убрать дубль `add`/`remove` vs `toggle` — оставить `toggle` и использовать его в `onChange` чекбокса-«все».

- **[MEDIUM]** Показывать имя (`offerId`, `name`) в таблице, а не только `offerId`. Сейчас колонки: Маркет, Артикул, Категория, Причина, Ошибка — но нет имени товара, из-за чего при длинных `offerId` строки нечитаемы.

- **[LOW]** Добавить счётчик отремонтированных vs всего в success-стрип для job-accepted-режима (сейчас показывается только `job.id`, без прогресса).
