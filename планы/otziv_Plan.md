# ReviewsPage — Plan

## Current State

Страница отзывов агрегирует отзывы с Ozon, Яндекс.Маркета и Wildberries в одном списке. Оператор видит карточки отзывов, может фильтровать по маркетплейсу и чекбоксу «только без ответа», отвечать на отзыв прямо с UI (с подтверждением через `window.confirm`), использовать готовые текстовые шаблоны и эмодзи-панель. Шаблоны CRUD-редактируются через `TemplatesDrawer`. Данные обновляются автоматически каждые 2 минуты.

## Bugs / Issues Found

- **`cleanText(review.status)` в `normalizeOzonReview` — потенциальный TypeError**
  Строка 43 (`02f-reviews-routes.js`): `needsReply: cleanText(review.status).toUpperCase() !== "PROCESSED"`. Если `review.status` — `null` или `undefined`, а `cleanText` возвращает пустую строку, это работает. Но если `cleanText` не определена в scope на момент вызова (зависит от порядка require), выброс — тихо ломает весь аккаунт Ozon. Проверить: нет явной защиты `String(review.status || "")`.

- **Нет кнопки «Ответить» блокируется после успеха, но состояние `open` сбрасывается, не `text`**
  Frontend `ReviewCard`, строки 51–55: `onSuccess` делает `setOpen(false)` и `setText("")` — это правильно. Но если пользователь снова открывает форму через кнопку «Ответить», предыдущий `reply.error` остаётся в мутации (TanStack Query не сбрасывает `error` при повторном `open`). Оператор видит старое сообщение об ошибке при повторном открытии, хотя прошлая отправка могла уже пройти.

- **`window.confirm` в `ReviewCard` блокирует UI-поток (строка 96 `ReviewsPage.tsx`)**
  `window.confirm("Отправить ответ? ...")` — синхронный вызов, блокирующий event loop в браузере. Не работает в iframe и ряде мобильных браузеров. В `QuestionsPage` такого `confirm` нет — поведение непоследовательное между страницами.

- **Отсутствует индикатор загрузки при первичном рендере**
  `ReviewsPage.tsx`, строка 178: состояние «пусто» показывается когда `!rows.length && !reviewsQuery.isFetching`. Но при первом открытии страницы, пока идёт загрузка (`isFetching=true`), контейнер `.reviews-grid` просто пустой — нет скелетона или спиннера. В `ChatsPage` использован `ListSkeleton` — здесь его нет.

- **`useMemo` для `counters` зависит только от `rows`, но не обновляется при смене фильтра до завершения запроса**
  Строки 126–130 `ReviewsPage.tsx`: `counters` вычисляется из `rows` (текущих данных в кеше). При переключении фильтра маркетплейс/unanswered новый запрос ещё идёт, а `rows` держит данные предыдущего запроса — `counters` показывает устаревшие цифры в `Stat`. Это стандартное поведение TanStack Query (staleTime=0), но видимо для оператора неочевидно.

- **Счётчик символов `{text.length}/5000` не блокирует отправку при превышении лимита**
  Строка 93–95 `ReviewsPage.tsx`: счётчик показывается, но кнопка «Отправить» отключена только при `!text.trim() || reply.isPending` — нет проверки `text.length > 5000`. Бэкенд WB сам режет до 5000 (`text.slice(0, 5000)`), но для Ozon/Yandex такого среза нет, и API маркетплейса вернёт ошибку.

- **В `normalizeYandexReview` поле `needsReply` всегда `true` при `needReaction === undefined`**
  Строка 65 (`02f-reviews-routes.js`): `needsReply: feedback.needReaction !== false`. Если Яндекс не прислал это поле (undefined), выражение `undefined !== false` = `true` — все отзывы Яндекса без явного `needReaction: false` помечаются как «ждёт ответа».

- **Дублирование отзывов при нескольких магазинах с одним `businessId` у Яндекса**
  Строки 137–158 (`02f-reviews-routes.js`): используется `seenBusinesses` для дедупликации по `businessId` — это сделано правильно. Но если у нескольких shop-конфигов разные `id` но один `businessId`, только первый попавший shop используется для вызова. Нет никакого предупреждения о пропущенных магазинах.

## Improvement Ideas

- **[HIGH]** Добавить проверку `text.length <= 5000` в кнопке отправки ответа — заблокировать кнопку при превышении лимита, добавить красный цвет счётчика. Для Ozon/Yandex лимит тоже должен резаться на бэкенде аналогично WB.

- **[HIGH]** Заменить `window.confirm` на модальный диалог или убрать его — в `QuestionsPage` его нет, поведение должно быть единообразным.

- **[HIGH]** Исправить `needsReply` для Яндекса: `feedback.needReaction === true` вместо `!== false`, чтобы undefined трактовался как «нет реакции не нужна», а не «нужна».

- **[MEDIUM]** Добавить `ListSkeleton` (или аналог) при первичной загрузке `reviews-grid`, как это сделано в ChatsPage.

- **[MEDIUM]** Сбрасывать состояние мутации (`reply.reset()`) при повторном открытии формы ответа (`setOpen(true)`), чтобы старая ошибка не отображалась.

- **[MEDIUM]** Добавить кнопку «Отметить как отвеченное» без отправки текста — полезно когда ответ уже дан вне системы (например, в личном кабинете). Для Ozon это `mark_review_as_processed: true` без создания комментария.

- **[MEDIUM]** Показывать фото к отзыву (`photosCount` уже есть в нормализаторе) — хотя бы счётчик «📷 2 фото» в карточке.

- **[LOW]** Добавить пагинацию или «Загрузить ещё» — сейчас лимит жёстко `50` в URL фронта, но бэкенд поддерживает до 300. При большом числе отзывов оператор не видит полный список.

- **[LOW]** Показывать название магазина/кабинета (поле `target`) в карточке когда подключено несколько кабинетов Ozon или несколько магазинов Яндекса.

- **[LOW]** Добавить сортировку или возможность фильтра по рейтингу (например, «только 1-2 звезды»).
